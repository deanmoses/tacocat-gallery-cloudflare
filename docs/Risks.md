# Risks

Risks that could stop pix.tacocat.com moving from AWS to Cloudflare, and what's been done to mitigate. Timings are [Globalping](https://globalping.io) probes from Paris, Marseille, Baton Rouge and Los Angeles, and `api/scripts/probe.sh` from Berkeley, with the D1 primary in SJC and read replication on. "Worker" is time spent inside the Worker; TTFB adds the visitor's connection. How performance is judged against the AWS site, and every measurement behind it, is in `docs/Perf.md`.

Status: ✅ solved, ⚠️ solved with a catch, ❌ fails today, ⏳ open or untested.

| 1   | TTFB > 100 ms                                        | ❌     | When a read reaches an active replica, TTFB is great: 41 to 130 ms (17 to 70 ms in the Worker), but most reads do not hit an active replica at our volume: the WEUR and ENAM replicas are inactive. | 2   | A derived image's first request at a colo is slow    | ⚠️     | Stored derivatives cached per colo through the Cache API take 17 to 66 ms warm. A colo's first request goes to R2 in WNAM, 250 to 550 ms from Baton Rouge and Paris, and at this traffic that is the usual case; an R2 custom domain with Tiered Cache was no faster. The AWS image CDN's misses take 271 ms at the median and 388 ms at p90. It is one step of a page load; what it costs the page is judged in `docs/Perf.md`. Album JSON is not edge-cached for the same reason: in a week of the AWS site's logs, most album views were the first of that page at that edge, a 35 to 40% hit rate (`docs/plans/EdgeCachedAlbums.md` in `tacocat-gallery-sam`). Next: a second derived bucket in WEUR, whose cold read from Paris is unmeasured. |
| 3   | The page and JS chunks are slow from a cold location | ✅     | Served from the visitor's colo on the first request: a Globalping probe on 2026-09-23 got `cf-cache-status: HIT` for an album page and an entry chunk no one had requested there, 20 to 34 ms to first byte from Paris and 127 to 171 ms from Baton Rouge (66 to 82 ms on a repeat). On AWS, the chunk missed on the first request (294 ms from Paris, 162 ms from Baton Rouge), and an album page, which CloudFront serves as an error response, went to the origin every time (286 to 290 ms from Paris). | 13  | R2 event notification to Queue to Worker is not a usable upload pipeline     | ⚠️     | An upload is processed within seconds. The consumer is idempotent (the version id comes from the event, the row is written before the original, the inbox object is deleted last), failures land in a dead-letter queue, and a rejected file becomes a row in `upload_error`, read with `POST /api/errors`. Only S3 API writes raise the event: a file written through the Cloudflare REST API, including `wrangler r2 object put` and the dashboard, is never processed.                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                  |
| 14  | Browser presigned PUT to R2 fails on CORS or needs a custom domain           | ✅     | The browser PUTs straight to R2 with a URL the Worker signs, given the bucket CORS rule in `api/r2-cors.json`.                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                             |
| 15  | Video: Stream cannot take iPhone HEVC, or an ffmpeg Container is too awkward | ⚠️     | ffmpeg in a Container turns iPhone HDR HEVC into a 1080p H.264 MP4 and a poster. `standard-2` is the production size: a 10 s 4K HDR clip takes about 35 s end to end and 0.2% of the monthly container allowance. Output is capped at 1080p because the tone-map dominates the time. The tone-map (hable, `desat=0`) is watchable but warmer and redder than the phone's own rendering. A file ffmpeg rejects becomes an upload error rather than a retry. Stream is untested.                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                             |
| 16  | Upload metadata extraction differs from Lambda                               | ✅     | Solved 2026-09-25. Workers have no `DOMParser`, and ExifReader skips the XMP packet without one, where in Node it loads `@xmldom/xmldom` by itself; the Worker now passes that parser in. It mattered more here than on AWS, which converted every HEIC to JPEG before reading it: a HEIC or PNG carries no IPTC, so a caption written in Adobe Bridge is XMP only, and every such upload had lost its title and keywords. `readImage` now takes the same fields in the same order as the Lambda's `selectMetadata`: IPTC Object Name, Headline, then XMP title and headline for the title; IPTC Caption/Abstract then XMP description; IPTC Keywords then XMP subject for the tags, which the Worker had not read at all, and IPTC Object Name under its real name, which it had misspelt. The unit test is the Lambda's own fixtures with the values its tests expect, so parity is what the test asserts; the HEIC cases fail without the parser. Reading a 497 KB HEIC or a Bridge-captioned JPEG takes about 1 ms in workerd, 4 ms at worst, on a clock 1 ms coarse. The bundle grew from 1371 to 1602 KiB, 267 to 315 KiB gzipped. GIF is untested. Fields Bridge writes that the Lambda ignored, city, country and copyright, are ignored here too. |

## Admin

| #   | Risk                                           | Status | Result                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                         |
| --- | ---------------------------------------------- | ------ | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------ |
| 17  | Passkey-only admin login is too much machinery | ✅     | Works, on an iPhone too: `/login`, `/invite/<token>` and a signed 30-day session cookie. A passkey is bound to the hostname, so an `Origin` allowlist picks the site, and `wrangler dev` needs `--local-upstream`. A login challenge lets someone in once: a D1 row records it until its cookie expires, since synced passkeys report a sign count of 0 and the count cannot catch a replay. A session cannot be revoked early: removing an admin means deleting their passkeys and rotating `SESSION_SECRET`, which logs every admin out. Who may be invited is the `user` table, seeded by a migration rather than a screen, and the passkey and invite tables reference it. |

| 19  | Three environments and CI cannot be driven from config          | ⚠️     | `infra/` (OpenTofu) declares the zone, bot and cache settings, D1, the buckets, the R2 custom domain, the queue and its notification; `api/wrangler.jsonc` owns the Worker, bindings, routes and crons, and the D1 schema ships as migrations. Provider gaps: no per-category AI crawler policies; R2 custom domains and event notifications cannot be imported; importing D1 needs `ignore_changes` on the location hint. One account API token has to be made by hand, since Wrangler's OAuth login stops at `zone:read`. CI runs on GitHub Actions and the repository's settings are a script (Continuous integration in `README.md`). Staging and production are two Workers from one `api/wrangler.jsonc`, each with its own data from an OpenTofu module instance (Environments in `README.md`). Deploys run in GitHub Actions (`.github/workflows/deploy.yml`) against GitHub Environments that `scripts/github-setup.sh` creates, with one account API token as the repository secret, the one thing made by hand; Workers Builds was tried first and dropped, since its deploys showed nowhere in GitHub and every setting of it was a dashboard field. The release is `scripts/release.sh` (Deploying in `README.md`): a version uploaded without traffic, the migrations, a check at 0% through the version-override header on the live hostname (a Worker with a Container gets no Version URL), then the switch, and a rollback if the live check fails. A pull request branch releases to staging on every push and a merge to `main` releases production, so merge is the promote. Not built: per-branch previews (Worker Previews, shipped 2026-09-22, do not reach the queue or the crons) and an alert on production errors after a release. |

The workflow runs from GitHub since this home network intercepts port 53 and answers every query itself whichever server it names, which made two unrelated nameservers look identical. Untried: the switch itself, and mail through it (send both ways, `DKIM: PASS` in Gmail's Show original).                                                                                                                                                                                                                                                                                                                                                                                      |
| 21  | Migrating the real gallery is slow or costly                    | ⚠️     | Priced and timed on 2026-09-24, not done. | 22  | No backup of the originals outside Cloudflare                   | ⚠️     | Built, not switched on. `scripts/backup-originals.sh` mirrors the production media bucket to a second provider with rclone, run nightly by `.github/workflows/backup.yml` an hour after the D1 dump (#9) lands in that bucket, so the dump is covered too.
