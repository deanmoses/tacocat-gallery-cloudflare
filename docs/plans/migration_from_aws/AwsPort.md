# Porting the AWS back end

The Worker in `api/` is the back end of pix.tacocat.com: every read, write and pipeline the AWS back end in `tacocat-gallery-sam` has, built as an improvement on it rather than a least-effort port, since Cloudflare's one repo, local bindings and simpler deploys are as much the reason to move as performance. This page keeps the decisions behind the design and what is left to do; `docs/Architecture.md` describes the system as built, and where the two disagree the code has moved on.

Decided on 2026-09-24; the port merged on 2026-09-25 and the resources were renamed for their environments on 2026-09-28.

## Goals

- **Every feature the web app has works**, against this Worker, with the app changed only where the change makes the whole system simpler or faster (`docs/plans/migration_from_aws/PerfVsAws.md` lists each difference).
- **Better engineered than the AWS version**: one atomic batch where AWS had a transaction plus hand-written cascades; a write-once object store where AWS copied files on every rename; tests against real local bindings where AWS tested against a deployed stack; layers the linter enforces where AWS documented them.
- **A foundation for decades.** Breaking changes to the API and the database were fine while nothing but the prototype used them; they will not be later.

Not part of the port, each with its own row in `docs/plans/migration_from_aws/AwsMigrationRisks.md`: the HEIC formats the Images binding rejects, sizing the transcoder for real video, moving `tacocat.com`'s nameservers, the external backup of the originals, and copying the real gallery over (`docs/plans/migration_from_aws/AwsDataMigration.md`).

The source was the AWS back end's `main`, with one contract change from its unmerged edge-caching branch: `getPeers`, `getPrevAndNext` and `getLatestAlbum` are not ported, since the app computes prev and next from the parent album and the latest album from the current year. The half-finished video data model was finished on the way: `itemType` is `album` or `media`, and every media item has `mediaType` `image` or `video`, which the database enforces.

## Principles

- **The database is the catalog and R2 is write-once.** An original is written exactly once, under a key that never changes, and the `item` row says which version of a media item is current. Every gallery operation, create, edit, publish, rename, set thumbnail, delete, is one D1 batch that touches no object. The only code that writes to a bucket is the upload pipeline, and nothing deletes an original, so restoring a deleted or replaced item is pointing a row at the old version.
- **A write's conditions are in the statement.** D1 has no interactive transactions: its one atomic unit is `batch()`, whose statements are fixed before any runs, and Drizzle's `transaction()` sends a `BEGIN` that D1 refuses. So a rule that depends on another row is a condition of the statement that writes, an `EXISTS` in the `WHERE` or an `INSERT … SELECT`, the statement's `meta.changes` says whether the rule held, and when it did not, one follow-up read finds out why and gives the `400` its message. The publish guard, the thumbnail's subtree check, the same-extension rename and the album rename are all written this way, and every such subquery gets a rows-read budget test.
- **One origin.** The app, the API, login and the media are served from the site's own hostname: the app's `/login`, and the Worker's `/api/*`, `/i/*`, `/v/*`, `/raw/*`. No `api.`, `auth.` or `img.` subdomain and no Cognito hosted UI on `login.tacocat.com`, so no CORS and no credentials option on a fetch. The one request that leaves the origin is the upload itself: the browser's presigned PUT goes to the account's R2 S3 endpoint, so the media bucket carries a CORS policy, in `infra/`, that allows PUT with a content type from each environment's site origin and from the local dev origin. AWS's S3 bucket had the same.
- **A path is for now; an id is for later.** A request names what it acts on by path, the URL scheme, and the statement resolves it as it runs, so a path that moved between the page loading and the click answers 404 and the admin refreshes. Anything the database keeps in order to act on later, an album's thumbnail, a replacement's target, an upload's album, references the row's id, and the database clears the reference when that row goes, so what it points at cannot be renamed or deleted out from under it. Text kept as a record and never resolved is the exception: `upload.target_path`, which still says an upload was a replacement after its target is gone, and `upload_error.path`, which the app polls by.
- **The shapes both sides agree on live in `shared/`**, as valibot schemas: every record, every request body, every response, the error body, the URL builders. The Worker maps rows to them; the app parses responses with them. Neither imports the other.
- **Layers the linter enforces.** Directories under `api/src` with import rules, in the same `no-restricted-imports` mechanism that holds the web app's layers, plus a cycle check.
- **Validate in the database where it can, and as near to it as possible where it cannot.** Every rule about a single row, required fields, no blanks, formats, one type's fields being null for the other, a crop fitting inside its image, is a `CHECK` or `NOT NULL` constraint in `schema.ts`, so no code path, the import endpoint and a hand-run script included, can write a row the rules forbid. What SQLite cannot express in a constraint, rules that look at other rows or inside a JSON array, is checked in `gallery/`: a cross-row rule as a condition of the writing statement, a JSON rule by the shared schema before the statement is built. Rows coming back out are parsed against a schema before anything reads them, as `albums.ts` does now.
- **Tests against real bindings**, per `docs/Testing.md`: D1, R2, the Queue and Images run locally; only the ffmpeg container and third-party HTTP are stood in for.

## Decisions

The choices that are not obvious from the code, each with its reason. The specifics they led to are in `docs/Architecture.md` and the code.

- **Objects are keyed by version id alone, never by gallery path.** A rename of a photo or an album is a database change and nothing else, where AWS copied every original and every derivative one object at a time. The URL the app uses keeps the path for whoever reads it, in logs and network tabs, and the Worker never checks it against the row, so a URL cached at the edge or in an email keeps working after a rename; the version is the secret. Given up: browsing a bucket by album in the dashboard, which `api/scripts/media.ts` and the path in each original's metadata stand in for.
- **The version id is minted at presign**, a millisecond timestamp and 64 random bits, and written to the `upload` table with what the upload is for, so the pipeline can read an R2 event whose key is only the id and refuse an object nobody presigned.
- **Any file may replace any media item**, PNG over JPEG, video over photo, because the row's identity is its id and the object's is its version; captions and album thumbnails carry over, and the crop only when the new image has exactly the old dimensions, since a rectangle that happens to fit another photo is a plausible-looking wrong thumbnail.
- **Originals are kept as uploaded, HEIC included**; the Images binding decodes HEIC, so nothing is converted on the way in, and `/raw/` answers a HEIC as a JPEG made on request for the one link a browser follows. AWS converted every HEIC on upload with HEIC-specific code at every layer.
- **An upload is PUT straight to its original's key, typed by its file's extension, and only its item depends on the pipeline** (2026-10-02, #136), as on AWS. The port had put an inbox bucket in front of the originals, told a file's type from its first bytes, and made the thumbnails and the media page's image a condition of the upload, so that the signing key could not write an original, a misnamed file was caught, and no album showed a broken image. Each cost more than it bought: the copy out of the inbox was a second write of every file and a place for reads to hang, and a busy image service failed uploads of files with nothing wrong with them. Now presign signs the PUT to `originals/<versionId>` with the content type the extension gives, the pipeline reads the original where it is, and the media page's image is made after the item is written, once, a failure only logged. The signing key can therefore write and delete originals, which is accepted.
- **The upload pipeline is a Workflow instance per event**, started by the queue consumer with a batch size of one, because Queues adds consumers only as a backlog grows and a drop of 52 photos ran one at a time; a Workflow gives each upload its own retries. It pre-generates the thumbnail and detail image so no first reader waits, and a file the binding refuses becomes an upload error rather than a broken image.
- **Search is FTS5 over a view of `item`**, two indexes, one stemmed and one exact for prefixes, with the caller's RediSearch syntax compiled to FTS5 matches so no input is a syntax error. Gained over RediSearch: accent folding and digits kept in names. Lost: fuzzy and optional terms, which the app never offered.
- **Rules a single row can state are `CHECK` constraints**, so no code path, a script included, can write a row the rules forbid; rules about other rows are conditions of the writing statement, and `meta.changes` says whether they held. A constraint failing is a bug and answers 500, except through the import endpoint, which names the constraint.
- **Routing is Hono's**, kept inside `index.ts` and `routes/`; `gallery/` and below take plain arguments. Hono dispatches a `HEAD` as a `GET` before any route matches, so the album and media handlers read the raw method and answer a `HEAD` with an existence check.
- **One origin.** App, API, login and media on one hostname, so no CORS and no credentials option on a fetch. The one request that leaves is the presigned upload to R2, which is why the originals bucket carries a CORS policy in `infra/`. One cost surfaced later: the app's own files and its thumbnails share one connection, which is why the service worker's precache had to go (`docs/plans/migration_from_aws/PerfVsAws.md`).
- **The media routes are not gated on who is asking**, as AWS's image CDN was not: knowing the version id is knowing the photo, and `/raw/` and `/v/` can reach nothing but that version's objects.
- **Headers and `robots.txt`** carry AWS's CloudFront policies over: `noindex` and the AI-training refusals on every response, the security set, `Cross-Origin-Resource-Policy: same-site` on media, a real `robots.txt` the zone prepends its AI-bot block to. The app's files get theirs from `web/static/_headers`, the Worker's from its wrapper, since two things serve responses.
- **Migrations were reset to one baseline** before the port merged, with both environments emptied by hand, since they held prototype data and seventeen migrations that rebuilt `item` three times.

## From AWS to the Worker

| AWS                                                           | Worker                                                                       |
| ------------------------------------------------------------- | ---------------------------------------------------------------------------- |
| `GetAlbum`, `AlbumExists`, `MediaExists`                      | `GET`/`HEAD /api/album`, `HEAD /api/media`                                   |
| `GetLatestAlbum`                                              | Dropped; the app reads it off the current year                               |
| `Search` on RediSearch, `DynamoToRedis` stream, `SyncRedis`   | `GET /api/search` on FTS5 in the same database; the triggers keep it in step |
| `CreateAlbum`, `UpdateAlbum`, `DeleteAlbum`, `RenameAlbum`    | `PUT`, `PATCH`, `DELETE /api/album`, `POST /api/album-rename`                |
| `SetAlbumThumbnail`                                           | `PATCH /api/album-thumb`, by row id                                          |
| `UpdateMedia`, `DeleteMedia`, `RenameMedia`, `RecutThumbnail` | `PATCH`, `DELETE /api/media`, `POST /api/media-rename`, `PATCH /api/thumb`   |
| `GenerateUploadUrls`, `GetErrors`                             | `POST /api/presigned`, `POST /api/errors`                                    |
| `ProcessMediaUpload` on an S3 event                           | A Workflow instance per R2 event, started by the queue consumer              |
| MediaConvert and `VideoTranscodingComplete`                   | The ffmpeg container, called from the same consumer                          |
| `GenerateDerivedImage` behind CloudFront                      | `GET /i/*` with the Images binding and the derived bucket                    |
| S3 versioning, `revertS3Version`, the 24-day expiry           | Write-once keys, and a row that points only at what succeeded                |
| Cognito and `tacocat-gallery-auth`                            | Passkeys, unchanged                                                          |
| The errors table with a TTL                                   | `upload_error`, purged nightly                                               |
| AWS Backup of the originals                                   | Not in this port; see Risks #22                                              |

## How it landed

The port was one pull request, one commit per step, each reviewed before the next, and merged on 2026-09-25 (#37) after a staging rehearsal that emptied staging's database, buckets and queues by hand, registered a passkey again and made the first browser upload on the new code. Production got the same at the merge, from 22:29 to 22:49 UTC, and the comparison album was imported again minutes later. Two things the rehearsal taught that the plan had not: a version release binds to a Workflow by name but does not create it, so the plain deploy had to run once before the first upload could complete, and the upload rate was Queues' fan-out, not the Worker's, which is why the pipeline became a Workflow instance per event.

On 2026-09-28 every resource was renamed for its environment (`production-*`, `staging-*`), and the media bucket split into one per role, because an R2 token scopes to whole buckets and the key the Worker signed uploads with could until then overwrite an original; the Worker's key now reaches `uploads` and `derived` alone, and the originals are written by the binding and nothing else. That is the one place the AWS design was cleaner: a Lambda presigned with its own role's temporary credentials, scoped to a prefix, and nobody stored a key. Each new Worker was deployed beside the old one and took the hostname over once its checks passed.

## Lessons

Things a fresh session would otherwise find out the hard way:

- Never `git stash` mid-change: new files are untracked until staged, and a stash drops them from the tree. The pre-commit hook runs every suite the staged files touch, so a commit takes about 40 seconds; commit once, when the change is green, rather than in pieces.
- The test helpers to reach for are `call`, `callAsAdmin` and `parseExactly` in `api/test/helpers.ts`. A stack test can import a constant from `api/src` to hold two copies of something together, as the headers test holds `web/static/_headers` to the Worker's values.
- What Hono does with `HEAD`, a mid-path `*` and a guest's write is under The API above; read it before adding a route.
- `import-x/no-cycle` sees `.ts` files only because the config names the extension; the comment there says so, so it is not a setting to tidy away.
- Wrangler's local Durable Object reset prints `Application called deleteAllDurableObjects()` as an uncaught exception during the tests. It is the Vitest Workers plugin's storage isolation, not a failing test.
- The stack tests start their Worker with no persisted storage, so D1 there has no tables at all; a route that reads D1 answers 500 there, which the routing test never looks at. List only paths that need no database in that test.
- **The write pattern is built; reuse it.** A gallery write is one statement whose cross-row rules are `EXISTS` subqueries in its `WHERE`, returning `Written`, the changes and D1's meta, from `api/src/gallery/writes.ts`. When it changed nothing, one read of subselects, `describeAlbum` or `describeMedia`, says why, and the route turns that into the 400 or 404 with the message the AWS lambda used. Routes read bodies with `parsedBody` and answer with `wrote` from `api/src/routes/requests.ts`, 204 with the bookmark cookie, which is all the app checks. The rows-read test has a case per write; add one for each new subquery.
- A Drizzle query builder is changed by what is called on it, so a builder reused for several subqueries silently gives them all the last `where`. Start each from `database.select()`.
- Drizzle's `run()` returns rows under their SQL column names, not the builder's aliases, so name a computed column in SQL with `.as()`; its `batch()` returns rows without D1's meta, so a write whose cost is watched runs its statements one at a time.
- D1's `meta.changes` counts what the FTS triggers wrote too, so a write tests for more than zero changes, never exactly one.
- A `CHECK` whose expression comes out `NULL` passes, so every constraint says what must be non-null, and D1 refuses a GLOB pattern over 50 characters, so a long format is checked in pieces or by a `strftime` round trip. `api/test/db/constraints.test.ts` tries every rule by name; add a row there for a new one.
- A statement in a `batch()` has to come from a query builder: Drizzle's D1 driver cannot batch a raw `sql` statement, and its insert from a select takes every column of the table, in the table's order, each aliased to its column name. `insertItem` in `api/src/gallery/upload.ts` is the example.
- The test admin is `moses`, a seeded user, because a presign records who asked and `upload.username` references `user`; a cookie for a made-up name gets a foreign key error on the first write that records it.
- `eslint --fix` turns `expect(a > b).toBe(true)` into `toBeGreaterThan`, which throws on strings. Compare timestamps with `Date.parse`.
- Presign takes only strict media names, what the app's sanitizer makes, so a test stages an upload under a lowercase name with underscores, not a fixture file's own.
- D1 binds at most 100 parameters to one statement, so rows go in as a batch of single-row inserts, never one multi-row insert; a drop of 52 photos found the presign insert doing the latter. Local D1 enforces the limit, so a test with a day's worth of rows catches it.
- A local Worker can consume no real queue, Wrangler's remote bindings leave Queues out, so under `wrangler dev` an upload could never complete: the browser's PUT went to the account's bucket and its event to the deployed Worker. The port first removed the prototype's stand-in on the grounds that the tests drive the queue themselves, which a person cannot. `UPLOAD_MODE=local` in `.dev.vars` brings it back as Cloudflare's local-first workflow wants it: presign answers with the Worker's own URL, `PUT /upload/<versionId>` puts the file in the local inbox and sends the local queue the message R2 would, and the pipeline runs unchanged. The e2e stack runs the same way, so its upload journey ends with the item in the album.

## Afterwards: copying the gallery

The real gallery, its rows and its originals, was copied into production on 2026-09-30 and verified, as `docs/plans/migration_from_aws/AwsDataMigration.md` describes.

## Afterwards: taking over the hostname

When `pix.tacocat.com` points here, a reader's browser still holds the AWS app's service worker for that origin, home-screen installs included, and asks this site for `/service-worker.js` on its update check. The app has no worker (`docs/plans/migration_from_aws/PerfVsAws.md`, _Differences from the AWS app_, 2026-09-27), so the asset router would answer with the fallback page, the update would fail on its content type, and the old worker would stay installed with its caches for good. So the release that takes the hostname ships a worker at that path whose activation deletes every cache and unregisters itself, with a test that fails without it (#152), and a later release removes it once the readers have visited (#153). A reader who never visits in between keeps the old worker, which answers only image requests, network first, so nothing breaks for them either way.
