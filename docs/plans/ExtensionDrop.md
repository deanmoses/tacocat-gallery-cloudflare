# Media names without extensions

This is a plan to take the file extension out of media names, so the photo at `/2001/06-15/felix.jpg` becomes `/2001/06-15/felix`, and to use the change to put every rule about gallery paths and names in one place.

## Why

This will simplify the overall system.

### It simplifies replacing a media item with one of a different type

Currently, the extension in the name forces the replacement to be a rename. An item's name is `felix.heic`, so dropping an edited JPG on it has to rename the item to `felix.jpg`, and that rename is written four times: `baseNameOf` in `presign.ts`, a `substr`/`instr` rebuild in the `UPDATE` of `replaceItem`, a third copy in `explain` for the error message, and `replacementPath` in the web app. Each copy comes with a check that no other item already holds the new name, and the web app has to decide where to navigate when the media page's URL changes under it. Without the extension, a replacement keeps its item's name, and all of that goes.

### It reduces a same-name class of upload error

Currently, two files of one photo can both be uploaded. For example, `felix.heic` and an edited `felix.jpg` are different names today, so uploading the edit into the same day makes a second item rather than offering to replace the first. Without extensions they are both `felix`, the unique key on `(parent_path, item_name)` refuses the second, and the app's collision check offers the replacement instead. This only catches the same base name: `felix_edited.jpg` is still a new item.

### The type is already stored

`media_type` says image or video, and the original's content type is on its R2 object. The name saying it too means two sources that must agree, which `shared/src/item.ts` enforces on every write and the pipeline relies on, since it picks the image or video branch by `isVideoName(upload.itemName)`.

### Path handling has grown copies that disagree

We are using this as an opportunity to rationalize our path handling, which has accreted organically over the years in multiple diverging AWS repos. An audit of `web/`, `api/` and `shared/` on 2026-09-26 found:

- The web app has its own path layer in `web/src/lib/utils/galleryPathUtils.ts`: `isValidAlbumPath`, `isValidYearAlbumPath`, `isValidDayAlbumPath`, `isValidMediaPath`, `isValidPath`, `getParentFromPath`, `getNameFromPath`, `getParentAndNameFromPath` and `albumPathToDate`, about 60 call sites between them. It imports none of the path functions in `shared/src/paths.ts`, which cover the same ground. The route matchers in `web/src/params/` are a third copy of the year, day and media rules, and the regex inside `albumPathToDate` a fourth.
- The copies disagree. `/2001/13-45/` passes the `day` matcher and then the album load throws, because `isValidAlbumPath` checks month and day ranges and the matcher does not. `/2001/06-15/My Photo.JPG` passes the `media` matcher and `shared`, fails `isValidMediaPath`, and so loses its admin buttons and sends its update to the album route. The web app accepts `.jpeg` where `shared` refuses it. The SQL `CHECK`s have no extension list and no lowercase rule.
- A media name is judged at three levels, `isMediaName`, `isStoredMediaName` and `isStrictMediaName`, plus `hasStrictExtension` for replacements. The levels exist because AWS names were never sanitized and carry their extensions.
- Extensions are split four ways: `baseNameOf` and `extensionOf` at the last dot, `RenameMediaButton` at the first, `deduplicateMediaPaths` by hand, which drops the last character of a name with no dot, and `toTitleFromFilename` by regex.
- A day album's title is computed from its path in four places, and the year is taken out of a path five ways, one of them `replaceAll('/', '')`.
- Six components append a slash to `page.url.pathname` to make an album path, and `AlbumBaseImpl.href` slices it off again, as does its `parentHref`, while `ThumbableBaseImpl.parentHref` does not.
- The year, day and day-album rules are written again as regexes in `api/src/routes/search.ts`, `api/scripts/import-album.ts`, `api/scripts/debugbear.ts` and `api/scripts/media.ts`, and as `GLOB`s in `api/src/db/schema.ts`. The version id rule is in `shared/src/urls.ts`, `api/src/routes/upload.ts` and `schema.ts`. The scripts cannot import `shared/` because its internal imports have no `.ts` extension, which the bundlers resolve and Node's own TypeScript loader does not.
- Found on the way: `/i/` does not percent-decode its path where `/raw/` and `/v/` do; `parseImageRequest` skips the media-path and version-id checks that `parseMediaVersion` makes; the search link's `returnPath` is not URI-encoded, in `config.ts` and in `Header.svelte`; `parentAlbumPath` has no caller and `albumsEnclosing` is only called by tests; `api/scripts/passkey-selftest.ts` writes an item the constraints refuse; `web/src/lib/utils/dimensionUtils.ts` redoes the detail-size arithmetic `shared/src/urls.ts` already has.

## Decisions

- **A media name is a strict base name, with no extension, everywhere.** Lowercase letters and digits with single underscores between them, which is what the sanitizer already makes of an upload's file name. The database, the Worker, the web app and the scripts apply the one rule, so the "stored" level for older AWS names goes.
- **Every AWS name is sanitized during the copy.** `My Photo.JPG` becomes `my_photo`. Nothing links to the AWS paths once the copy rewrites the links, so there is no reason to keep a name the rule would refuse.
- **Collisions are resolved with `_n`.** Where two AWS items in one day album come out as the same name, a Live Photo's `img_1234.jpg` and `img_1234.mov` or `Felix.jpg` and `felix.JPG`, the photos come before the videos, so the still keeps the name and the clip gets `_2`, and among those of one kind the AWS names' own order decides, by code point. The order is fixed rather than dated because AWS kept no creation date and the date it did keep moves with every edit, while AWS stays live under the copy: a mapping that changed between the copy of one album and the links written into another would point those links at the wrong item, and a rerun of the import would swap `felix` and `felix_2` through replacements. The uploader's own `_n` looks only within one drop, so dropping `a.jpg` and `a.png` into an album that already holds `a_2` offers to replace `a_2`, which is accepted. The copy reports every rename it made.
- **Links in the gallery are rewritten, and links from outside are redirected.** The copy rewrites every link in a description or summary that resolves to an AWS media path to the item's new path, and a link it cannot resolve is reported and left as it is. Media URLs have also been shared by email and text for twenty-five years, so the app keeps answering the old form: the `media` route matcher accepts a name with an extension, and the media page's load sends the reader on to the sanitized base name. The app runs entirely in the browser, so that is a navigation inside it and the HTTP answer for the old URL is the app itself, not a 301: a person lands in the right place, and a crawler or a link preview does not, which is accepted, since the links were shared between people. That is wrong only for an item the copy renamed with `_n`, which the copy's report enumerates and which is accepted. Album URLs do not change.
- **A day name is a real calendar date in its year.** `02-30` is refused along with `13-45`, and `02-29` outside a leap year, by the Worker, the app's loads and the database alike. The constraint checks it the way the timestamp checks do, by round trip: `date(substr(parent_path, 2, 4) || '-' || item_name)` is the text it was given only for a real date. It is per row and costs nothing. The SvelteKit `day` matcher sees only its own segment, so it checks the shape and the page's load judges the calendar through `parsePath`, answering 404 for a day it does not have.
- **The databases are emptied and the migrations start over from zero.** Staging and production each hold a single imported album, which have to go before the copy from AWS anyway. The name rule changes `item`'s `CHECK`s, which SQLite can only do by rebuilding the table, and with no rows to carry across, a reset from one baseline is cheaper than the three-migration rebuild and its snapshot dance, which is why a second reset a day after the first. `api/migrations/` is reset as it was on 2026-09-25: one migration generated from `schema.ts`, one raw-SQL migration for the FTS5 tables, their view and their triggers, which folds `search_index_rebuilt.sql` into it, and one that seeds the users, the FTS one carrying the `-- resets: <reason>` line `scripts/lint.sh` lets delete the committed ones, since a generated migration is never edited. The snapshot and journal in `api/migrations/meta/` are generated afresh with them. Each database is emptied by hand, every table and `d1_migrations` together, after a table-at-a-time export, by the checklists under Pushing the port to staging and Releasing the port to production in `docs/plans/AwsPort.md`. The passkeys go with it; the one admin registered, on staging, registers again through `api/scripts/invite.sh`. The release's check that the previous version still works fails on that push, as it did then, and `wrangler rollback` cannot cross it.
- **The file's type comes from its bytes.** The pipeline reads the first bytes of the inbox object and tells JPEG, PNG, GIF, WebM and MKV (EBML), AVI (RIFF) and MPEG program streams apart by their signatures, and the ISO base media formats by their `ftyp` brand: `heic`, `heix`, `hevc`, `hevx`, `mif1` and `msf1` are HEIF images, the rest MP4, MOV, M4V and 3GP video. The sniffer answers the media type, the content type and the extension a download of it should carry, or refuses bytes that are none of these, which becomes the upload error the admin sees. The pipeline branches on that answer, and the original is stored with the sniffed content type rather than whatever the browser sent. Presign no longer needs the file's name and cannot refuse a file by type; the app's picker still filters by the extension lists, and a file that gets past it is refused by the pipeline instead. `/raw/` decides on the HEIC conversion from the original's content type and names the download from the item's name plus the extension for that type. The video branch reads the bytes by a range request before the transcode, since it never reads the whole file itself.
- **A replacement keeps its target's name.** An entry of the presign request is `{ path, replace?: true }`: the path the item has or will have, and whether an item there is being replaced, which the app asks the admin before saying. `upload.target_path` goes, since it would always equal the upload's own path, and a boolean `replacement` column keeps the record that an upload was one after `target_id` is cleared by the target's deletion. The pipeline's `UPDATE` changes the file, the type and the size, keeps the name, and keeps the crop only when the size is unchanged, as now.
- **The confirmation names the types when they differ.** Replacing a photo with a video, or a video with a photo, is allowed and works as any replacement does. But an iPhone Live Photo exports as a still and a three-second clip with one base name, so with extensions gone, dropping the clip on an album that already holds the still asks the same question an edited copy of the photo would. The prompt therefore says "replace the photo img_1234 with a video?" rather than "replace img_1234?", so that an admin who took the question to mean the usual thing does not turn a photo into its own clip.

## Target design

### One path module in `shared/`

`shared/src/paths.ts` is the only place a gallery path is parsed or a name is judged:

- `parsePath(path)` answers the root, a year album, a day album or a media item, each with its `parentPath`, its `name` and, for an album, its date, or `null` for anything else. It replaces `albumKey`, `mediaKey`, `isAlbumPath`, `isDayAlbumPath`, `isMediaPath` and `parentAlbumPath` on the Worker's side, and every validator, splitter and date parser in `galleryPathUtils.ts` on the app's.
- `albumPath` and `mediaPath` stay the only builders. The route loaders, the new-album and rename buttons, `UploadMachine` and `latestAlbum.ts` call them rather than writing template strings.
- `pathOfUrl(pathname)` turns a page's URL into its gallery path, in place of the six places that append a slash, and `hrefOf(path)` is its inverse, in place of the slicing in `AlbumBaseImpl` and the lack of it in `ThumbableBaseImpl`. The app's URLs have no trailing slash and a name no longer says what it names, so `pathOfUrl` goes by depth: three segments is a media item, fewer is an album.
- One function gives a day album's title and one its year, used by the album models, the navigation, the year page and search. `toTitleFromFilename` loses its extension strip and becomes a title from a name, beside them.
- `isMediaName` and `sanitizeMediaName` are the name rule and the sanitizer, and `deduplicateNames` the `_n` rule, `${name}_${n}`, so the copy and the uploader resolve a collision by the one function. The extension lists are about the app's file picker and nothing else, and nothing calls anything on a gallery path to learn a type.
- `shared/src/` spells its internal imports with their `.ts` extension, so that `web/src/params/` and the scripts in `api/scripts/` import the rules from it and the sanitizer the copy uses is the one the uploader uses.

### The database rules come from the same definitions

The `GLOB` builders in `api/src/db/schema.ts` become the SQL forms of the rules in `shared/`, with a test that feeds both the same names and paths and expects the same answers. `versionIdSql` and the `VERSION_ID` in `routes/upload.ts` go the same way. `item_path_check`, `upload_path_check` and `upload_error_path_check` take the name without an extension, and the day album's date is checked by round trip. The `upload` table loses `target_path` and gains `replacement`.

### The Worker loses the rename

`replaceItem` sets the version, type, size and duration and keeps `item_name`; the `taken` subquery, the name rebuild, its rows-read budget test and its branch of `explain` go, leaving `explain` two answers, a deleted album or target and a taken name. `presign.ts` loses `hasStrictExtension` and the base-name comparison. `renameMediaRoute` loses the must-keep-the-extension check. `isGalleryKey` in `shared/src/item.ts` loses the video-by-extension cross-check, so `mediaType` on a write is the only source of the type. `routes/images.ts` decodes the `/i/` path and parses it with the same checks as `/raw/` and `/v/`. `api/src/media/` gains the sniffer, and the pipeline branches on its answer rather than on the name.

### The web app loses its path layer

`galleryPathUtils.ts` is reduced to `sanitizeDayAlbumName`, renamed for what it does, since it is used for years as well. `replacementPath` and the navigation after an other-format replacement go. `markReplacements` compares names, which is now all a name is, and reports the target's type beside the file's for the confirmation. `fileFormats.ts` keeps only its file-side half, which the picker and the preview call with a `File`; the processing timeout is chosen from the upload's file, and an item's type is `mediaType` on its record. `config.ts` loses `createAlbumUrl`, `originalMediaUrl`, `videoPlaybackUrl` and one of the identical `updateUrl` and `deleteUrl`. `dimensionUtils.ts` calls `detailSize`. The media page's load redirects a path whose name carries an extension.

## Order of work

One PR with the following commits, each reviewed on its own and each leaving `npm run quality` green, with the tests `docs/Testing.md` asks for and the docs its change makes wrong. The first three are refactors that change no name: they put every rule in one place and take the file's type off the name, so that the fourth, the one that needs the databases emptied, is mostly deleting code. Every push releases the branch's head to staging, so staging is emptied before the first push that carries the fourth commit, and production before the merge.

### `shared/` for the scripts, and one source for the database's rules

Give `shared/src/` its `.ts` import extensions, and move `media.ts`, `import-album.ts`, `check-gallery.ts` and `debugbear.ts` onto its parsers in place of their own regexes. Have `schema.ts` build its `GLOB`s from definitions `shared/` exports beside the TypeScript rules, with a test that feeds both the same names and paths and expects the same answers, which is what keeps the SQL and the code from drifting apart again. No behaviour changes, no migration.

### One path module, under today's rules

`parsePath`, `pathOfUrl`, `hrefOf` and the title and year helpers in `shared/`; the web app, the route matchers and the Worker's routes moved onto them; `galleryPathUtils.ts` emptied of its path rules; `parseImageRequest` and `parseMediaVersion` made to check alike; the duplicates in `config.ts` and `dimensionUtils.ts` removed; `passkey-selftest.ts` fixed or deleted; the dead exports deleted; each bug above fixed with a test that fails without its fix. Names keep their extensions in this step, and where the copies disagreed the stricter rule wins: calendar-valid days, and `jpeg` refused.

### The file's type from its bytes

The sniffer, with a test per format from the smallest real file of each; the pipeline branching on its answer, the video branch reading a range first; `storeOriginal` writing the sniffed content type; `/raw/` deciding on the HEIC conversion by content type. No migration. After this nothing on the Worker reads a type from an item's name, while names still carry extensions and `isGalleryKey` still checks that the two agree.

### Names without extensions, and the migrations from zero

The name rule in `shared/` and so in the `CHECK`s, with the date round trip; the migration reset, with `replacement` in place of `target_path`; the presign entry as `{ path, replace }`; the replacement without the rename, in `replaceItem`, `explain`, `presign.ts` and the web app; the confirmation that names the types; the rename route without its extension check; the web app's upload, replace and rename; the redirect from a media URL with an extension; `ops/seed.ts`; and every test fixture that names an item `*.jpg`, which on 2026-09-26 was 818 mentions in 47 files, so the commit is mostly mechanical and is reviewed as such. Both databases and both environments' `originals/**` and `derived/**` are emptied, staging's before this commit is first pushed and production's before the merge; the one album production measures is imported again after the merge with the `import-album.ts` of the fifth commit. `docs/Perf.md` notes the gap and the URL change, since the AWS app's media URLs keep their extension and a measurement is read against what both sites were doing.

### The copy speaks the new names

`check-gallery.ts` reports every AWS name the sanitizer changes, every collision and the `_n` it resolves to, and every link in a description or summary with what it resolves to or that it does not. `import-album.ts` renames with the same mapping, rewrites links, and sets album thumbnails by the new paths, while downloading each original by its AWS path; a link to another album's item it resolves by the sanitizer alone, which is right unless that item collided in its own day, since one album at a time is all it sees. The mapping and the rewriting are one module the two scripts share, `api/scripts/aws-names.ts`, with a unit test.

## Out of scope

- The copy of the whole gallery, which step 3 prepares for but does not run.
