# Media names without extensions

This is the plan to take the file extension out of media names, so the photo at `/2001/06-15/felix.jpg` becomes `/2001/06-15/felix`, and to use the change to put every rule about gallery paths and names in one place. Only this plan is written so far; none of the work below has been started.

Decided on 2026-09-26. Where this page and the code disagree, the code has moved on and this page is history.

## Why

**An extension in the name makes a replacement a rename.** An item's name is `felix.jpg`, so dropping an edited PNG on it has to rename the item to `felix.png`, and that rename is written four times: `baseNameOf` in `presign.ts`, a `substr`/`instr` rebuild in the `UPDATE` of `replaceItem`, a third copy in `explain` for the error message, and `replacementPath` in the web app. Each copy comes with a check that no other item already holds the new name, and the web app has to decide where to navigate when the media page's URL changes under it. Without the extension, a replacement keeps its item's name, and all of that goes.

**Two files of one photo can both go out.** `felix.heic` and an edited `felix.jpg` are different names today, so uploading the edit into the same day makes a second item rather than offering to replace the first. Without extensions they are both `felix`, the unique key on `(parent_path, item_name)` refuses the second, and the app's collision check offers the replacement instead. This only catches the same base name: `felix_edited.jpg` is still a new item.

**The type is already stored.** `media_type` says image or video, and the original's content type is on its R2 object. The name saying it too means two sources that must agree, which `shared/src/item.ts` enforces on every write and the pipeline relies on, since it picks the image or video branch by `isVideoName(upload.itemName)`.

**Path handling has grown copies that disagree.** An audit of `web/`, `api/` and `shared/` on 2026-09-26 found:

- The web app has its own path layer in `web/src/lib/utils/galleryPathUtils.ts`: `isValidAlbumPath`, `isValidYearAlbumPath`, `isValidDayAlbumPath`, `isValidMediaPath`, `isValidPath`, `getParentFromPath`, `getNameFromPath`, `getParentAndNameFromPath` and `albumPathToDate`, about 60 call sites between them. It imports none of the path functions in `shared/src/paths.ts`, which cover the same ground. The route matchers in `web/src/params/` are a third copy of the year, day and media rules, and the regex inside `albumPathToDate` a fourth.
- The copies disagree. `/2001/13-45/` passes the `day` matcher and then the album load throws, because `isValidAlbumPath` checks month and day ranges and the matcher does not. `/2001/06-15/My Photo.JPG` passes the `media` matcher and `shared`, fails `isValidMediaPath`, and so loses its admin buttons and sends its update to the album route. The web app accepts `.jpeg` where `shared` refuses it. The SQL `CHECK`s have no extension list and no lowercase rule.
- A media name is judged at three levels, `isMediaName`, `isStoredMediaName` and `isStrictMediaName`, plus `hasStrictExtension` for replacements. The levels exist because AWS names were never sanitized and carry their extensions.
- Extensions are split four ways: `baseNameOf` and `extensionOf` at the last dot, `RenameMediaButton` at the first, `deduplicateMediaPaths` by hand, which drops the last character of a name with no dot, and `toTitleFromFilename` by regex.
- A day album's title is computed from its path in four places, and the year is taken out of a path five ways, one of them `replaceAll('/', '')`.
- Six components append a slash to `page.url.pathname` to make an album path, and `AlbumBaseImpl.href` slices it off again, while `ThumbableBaseImpl.parentHref` does not.
- The year, day and day-album rules are written again as regexes in `api/src/routes/search.ts`, `api/scripts/import-album.ts`, `api/scripts/debugbear.ts` and `api/scripts/media.ts`, and as `GLOB`s in `api/src/db/schema.ts`. The version id rule is in `shared/src/urls.ts`, `api/src/routes/upload.ts` and `schema.ts`.
- Found on the way: `/i/` does not percent-decode its path where `/raw/` and `/v/` do; `parseImageRequest` skips the media-path and version-id checks that `parseMediaVersion` makes; the search link's `returnPath` is not URI-encoded, in `config.ts` and in `Header.svelte`; `parentAlbumPath` has no caller and `albumsEnclosing` is only called by tests; `api/scripts/passkey-selftest.ts` writes an item the constraints refuse; `web/src/lib/utils/dimensionUtils.ts` redoes the detail-size arithmetic `shared/src/urls.ts` already has.

## Decisions

- **A media name is a strict base name, with no extension, everywhere.** Lowercase letters and digits with single underscores between them, which is what the sanitizer already makes of an upload's file name. The database, the Worker, the web app and the scripts apply the one rule, so the "stored" level for older AWS names goes.
- **Every AWS name is sanitized during the copy.** `My Photo.JPG` becomes `my_photo`. Nothing links to the AWS paths once the copy rewrites the links, so there is no reason to keep a name the rule would refuse.
- **Collisions are resolved with `_n`.** Where two AWS items in one day album come out as the same name, a Live Photo's `img_1234.jpg` and `img_1234.mov` or `Felix.jpg` and `felix.JPG`, the earliest created keeps the name and each later one gets `_2`, `_3` and so on, in creation order, as the uploader already does for two files of one drop. The copy reports every rename it made.
- **Links are rewritten, not redirected.** The copy rewrites every link in a description or summary that resolves to an AWS media path to the item's new path. No redirect from the old form is built. A link the copy cannot resolve is reported and left as it is.
- **The databases are emptied and the migrations start over from zero.** Staging and production each hold a single imported album, which have to go before the copy from AWS anyway, so no existing row's name is rewritten by a migration, and nothing forces the history of how the schema got here to be kept. `api/migrations/` is reset as it was on 2026-09-25: one migration generated from `schema.ts`, one raw-SQL migration for the FTS5 tables, their view and their triggers, which folds `search_index_rebuilt.sql` into it, and one that seeds the users, the first carrying the `-- resets: <reason>` line `scripts/lint.sh` lets delete the committed ones. The snapshot and journal in `api/migrations/meta/` are generated afresh with them. Each database is emptied by hand, every table and `d1_migrations` together, after a table-at-a-time export, by the checklists under Pushing the port to staging and Releasing the port to production in `docs/plans/AwsMigration.md`; the passkeys go with it, so each admin registers again through `api/scripts/invite.sh`. The release's check that the previous version still works fails on that push, as it did then, and `wrangler rollback` cannot cross it.
- **The file's type comes from the file.** The presign request says each upload's file name. The Worker checks the extension against the lists in `shared/`, derives the media type and the content type from it, writes both onto the `upload` row, and signs the content type into the PUT, so the original's stored content type is the one the Worker chose rather than whatever the browser sent. The pipeline branches on the row's `media_type`. `/raw/` decides on the HEIC conversion from the original's content type and names the download from the item's name plus an extension for that content type.
- **A replacement keeps its target's name.** An entry of the presign request that replaces an item names the item it replaces and no new path. The pipeline's `UPDATE` changes the file, the type and the size, keeps the name, and keeps the crop only when the size is unchanged, as now.

## Target design

**One path module in `shared/`.** `shared/src/paths.ts` is the only place a gallery path is parsed or a name is judged:

- `parsePath(path)` answers the root, a year album, a day album or a media item, each with its `parentPath`, its `name` and, for an album, its date, or `null` for anything else. It replaces `albumKey`, `mediaKey`, `isAlbumPath`, `isDayAlbumPath`, `isMediaPath` and `parentAlbumPath` on the Worker's side, and every validator, splitter and date parser in `galleryPathUtils.ts` on the app's.
- A day name is a real calendar date in its year, so `02-30` is refused along with `13-45`, and `02-29` only in a leap year, by the route matchers and the Worker alike. The database's `GLOB` goes on checking only the shape, unless `date()` proves an exact check cheap enough to put in the constraint.
- `albumPath` and `mediaPath` stay the only builders. The route loaders, the new-album and rename buttons, `UploadMachine` and `latestAlbum.ts` call them rather than writing template strings.
- `pathOfUrl(pathname)` turns a page's URL into its gallery path, in place of the six places that append a slash.
- One function gives a day album's title and one its year, used by the album models, the navigation, the year page and search.
- `isMediaName` and `sanitizeMediaName` are the name rule and the sanitizer. The extension lists, `extensionOf` and a `fileFacts(fileName)` returning media type and content type are about uploaded files only, and nothing calls them on a gallery path.
- `web/src/params/` imports the rules from `shared/`, and so do the scripts in `api/scripts/`, so the sanitizer the copy uses is the one the uploader uses.

**The database rules come from the same definitions.** The `GLOB` builders in `api/src/db/schema.ts` become the SQL forms of the rules in `shared/`, with a test that feeds both the same names and paths and expects the same answers. `versionIdSql` and the `VERSION_ID` in `routes/upload.ts` go the same way. `item_path_check`, `upload_path_check`, `upload_target_check` and `upload_error_path_check` take the name without an extension. The `upload` table gains `media_type` and `content_type`.

**The Worker loses the rename.** `replaceItem` sets the version, type, size and duration and keeps `item_name`; the `taken` subquery, the name rebuild and its branch of `explain` go. `presign.ts` loses `hasStrictExtension` and the base-name comparison. `renameMediaRoute` loses the must-keep-the-extension check. `routes/images.ts` decodes the `/i/` path and parses it with the same checks as `/raw/` and `/v/`.

**The web app loses its path layer.** `galleryPathUtils.ts` is reduced to what is not a path rule, if anything: `deduplicateMediaPaths` and `sanitizeDayAlbumName`, renamed for what it does, since it is used for years as well. `replacementPath` and the navigation after an other-format replacement go. `markReplacements` compares base names, which is now all a name is. `fileFormats.ts` takes the upload's file for the processing timeout and the item's `mediaType` for display. `config.ts` loses `createAlbumUrl`, `originalMediaUrl`, `videoPlaybackUrl` and one of the identical `updateUrl` and `deleteUrl`. `dimensionUtils.ts` calls `detailSize`.

## Order of work

One pull request of five commits, each reviewed on its own and each leaving `npm run quality` green, with the tests `docs/Testing.md` asks for and the docs its change makes wrong. The first three are refactors that change no name: they put every rule in one place and take the file's type off the name, so that the fourth, the one that needs the databases emptied, is mostly deleting code. Every push releases the branch's head to staging, so staging is emptied before the first push that carries the fourth commit, and production before the merge.

1. **`shared/` for the scripts, and one source for the database's rules.** Make `shared/` importable from `api/scripts/`, whose Node resolves the package's imports differently from the Worker's bundler, and move `media.ts`, `import-album.ts`, `check-gallery.ts` and `debugbear.ts` onto its parsers in place of their own regexes. Have `schema.ts` build its `GLOB`s from definitions `shared/` exports beside the TypeScript rules, with a test that feeds both the same names and paths and expects the same answers, which is what keeps the SQL and the code from drifting apart again. No behaviour changes, no migration.
2. **One path module, under today's rules.** `parsePath`, `pathOfUrl` and the title and year helpers in `shared/`; the web app, the route matchers and the Worker's routes moved onto them; `galleryPathUtils.ts` emptied of its path rules; `parseImageRequest` and `parseMediaVersion` made to check alike; the duplicates in `config.ts` and `dimensionUtils.ts` removed; `passkey-selftest.ts` fixed or deleted; the dead exports deleted; each bug above fixed with a test that fails without its fix. Names keep their extensions in this step, and where the copies disagreed the stricter rule wins: calendar-valid days, and `jpeg` refused.
3. **The file's type from the file.** The presign body carries each upload's file name; the Worker derives the media type and content type from it and writes them onto the `upload` row through an additive generated migration, which the reset in the next commit folds into the baseline; the PUT is signed with the content type; the pipeline branches on the row's `media_type`; `/raw/` decides on the HEIC conversion by content type. After this nothing on the Worker reads a type from an item's name, and names still carry extensions.
4. **Names without extensions, and the migrations from zero.** The name rule in `shared/` and so in the `CHECK`s; the migration reset; the replacement without the rename, in `replaceItem`, `explain`, `presign.ts` and the web app; the rename route without its extension check; the web app's upload, replace and rename; `ops/seed.ts`; and every test fixture that names an item `*.jpg`. Both databases and both environments' `originals/**` and `derived/**` are emptied, staging's before this commit is first pushed and production's before the merge; the one album production measures is imported again after the merge with the `import-album.ts` of the fifth commit. `docs/Perf.md` notes the gap and the URL change, since the AWS app's media URLs keep their extension and a measurement is read against what both sites were doing.
5. **The copy speaks the new names.** `check-gallery.ts` reports every AWS name the sanitizer changes, every collision and the `_n` it resolves to, and every link in a description or summary with what it resolves to or that it does not. `import-album.ts` renames with the same mapping, rewrites links, and sets album thumbnails by the new paths, while downloading each original by its AWS path.

## Not in this plan

- The nightly purge of objects no row references, which `docs/plans/AwsMigration.md` describes and which is still owed. Replacements leave their old versions in R2 until it exists, as they do now.
- The copy of the whole gallery, which step 3 prepares for but does not run.
