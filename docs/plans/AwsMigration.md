# Porting the AWS back end

This is the plan to port the AWS back end to Cloudflare. We're not 100% sure we're migrating yet, but we're seeing that Cloudflare provides an opportunity to improve on AWS in ways other than perf: developer experience, ease of modifying the system, easy of AIs reasoning about and modifying a singe repo rather than AWS's four repos. So rather than a straight least-effort port, let's use this as an opportunity to improve what exists.

The Worker in `api/` becomes the production back end of pix.tacocat.com: every read, write and pipeline the AWS back end in `tacocat-gallery-sam` has, built on what the prototype proved, with the parts of the prototype that were only for measurement kept and the parts that were shortcuts replaced. This page records the decisions, the target design, how each AWS piece maps onto the Worker, and the order the work lands in.

Decided on 2026-09-24. Where this page and the code disagree, the code has moved on and this page is history.

## Goals

- **Every feature the web app has works**, against this Worker, with the web app changed only where the change makes the whole system simpler. The web app was copied from `tacocat-gallery-sveltekit` at commit 8c57e5f of its `claude/getalbum-caching-nextprev-as8yq8` branch, which computes an album's prev and next from its parent and the latest album from the current year, so the API needs neither.
- **Better engineered than the AWS version**, not a like-for-like port: one atomic batch where AWS had a transaction plus hand-written cascades; a write-once object store where AWS copied files on every rename; tests against real local bindings where AWS tested against a deployed stack; layers the linter enforces where AWS documented them.
- **A foundation for decades.** Breaking changes to the API and the database are fine now, since nothing but the prototype uses them; they will not be later.

Not goals of this port, each with its own row in `docs/Risks.md` or its own later plan: the HEIC formats the Images binding rejects, 10-bit and some non-iPhone files, which until the container fallback in Risks #11 is built cannot be uploaded and have to be converted by hand first; sizing the transcoder for real video, moving `tacocat.com`'s nameservers, the external backup of the originals, and copying the real gallery over (sketched at the end).

## Sources

The AWS back end's `main` is the source, not the edge-caching branch. The branch, `claude/getalbum-caching-nextprev-as8yq8`, was never merged; it is one commit that drops prev/next from `getAlbum`, deletes the latest-album endpoint, and builds CloudFront edge caching that `docs/plans/EdgeCachedAlbums.md` in that repo concludes does not pay. `main` is about seventy commits ahead of it, with lint refactors across nearly every file, restructured integration suites, verified auth on reads and the publish guard moved inside the write. The port takes `main`'s logic and applies the branch's contract change by not porting `getPeers`, `getPrevAndNext` and `getLatestAlbum`.

The video support added to AWS in January 2026 left its data model half migrated: every media row has `itemType: 'image'`, only videos carry `mediaType`, and the types say so in comments. The port finishes it, as `shared/` already does: `itemType` is `'album'` or `'media'`, and every media item has `mediaType` `'image'` or `'video'`, which the database enforces.

## Principles

- **The database is the catalog and R2 is write-once.** An original is written exactly once, under a key that never changes, and the `item` row says which version of a media item is current. Every gallery operation, create, edit, publish, rename, set thumbnail, delete, is one D1 batch that touches no object. The only code that writes to a bucket is the upload pipeline; the only code that deletes from one is the nightly purge.
- **A write's conditions are in the statement.** D1 has no interactive transactions: its one atomic unit is `batch()`, whose statements are fixed before any runs, and Drizzle's `transaction()` sends a `BEGIN` that D1 refuses. So a rule that depends on another row is a condition of the statement that writes, an `EXISTS` in the `WHERE` or an `INSERT … SELECT`, the statement's `meta.changes` says whether the rule held, and when it did not, one follow-up read finds out why and gives the `400` its message. The publish guard, the thumbnail's subtree check, the same-extension rename and the album rename are all written this way, and every such subquery gets a rows-read budget test.
- **One origin.** The app, the API, login and the media are served from the site's own hostname: `/api/*`, `/login`, `/i/*`, `/v/*`, `/raw/*`. No `api.`, `auth.` or `img.` subdomain and no Cognito hosted UI on `login.tacocat.com`, so no CORS and no credentials option on a fetch. The one request that leaves the origin is the upload itself: the browser's presigned PUT goes to the account's R2 S3 endpoint, so the media bucket carries a CORS policy, in `infra/`, that allows PUT with a content type from each environment's site origin and from the local dev origin. AWS's S3 bucket had the same.
- **A path is for now; an id is for later.** A request names what it acts on by path, the URL scheme, and the statement resolves it as it runs, so a path that moved between the page loading and the click answers 404 and the admin refreshes. Anything the database keeps in order to act on later, an album's thumbnail, a replacement's target, an upload's album, references the row's id, and the database clears the reference when that row goes, so what it points at cannot be renamed or deleted out from under it. Text kept as a record and never resolved is the exception: `upload.target_path`, which still says an upload was a replacement after its target is gone, and `upload_error.path`, which the app polls by.
- **The shapes both sides agree on live in `shared/`**, as valibot schemas: every record, every request body, every response, the error body, the URL builders. The Worker maps rows to them; the app parses responses with them. Neither imports the other.
- **Layers the linter enforces.** Directories under `api/src` with import rules, in the same `no-restricted-imports` mechanism that holds the web app's layers, plus a cycle check.
- **Validate in the database where it can, and as near to it as possible where it cannot.** Every rule about a single row, required fields, no blanks, formats, one type's fields being null for the other, a crop fitting inside its image, is a `CHECK` or `NOT NULL` constraint in `schema.ts`, so no code path, the import endpoint and a hand-run script included, can write a row the rules forbid. What SQLite cannot express in a constraint, rules that look at other rows or inside a JSON array, is checked in `gallery/`: a cross-row rule as a condition of the writing statement, a JSON rule by the shared schema before the statement is built. Rows coming back out are parsed against a schema before anything reads them, as `albums.ts` does now.
- **Tests against real bindings**, per `docs/Testing.md`: D1, R2, the Queue and Images run locally; only the ffmpeg container and third-party HTTP are stood in for.

## Data model

Every table gets `created_at` and `updated_at`, from one shared Drizzle column set, with `updated_at` set by Drizzle's `$onUpdate` hook on every query-builder update and explicitly by the upsert helper. Both come from SQLite's clock: `created_at` by its default and `updated_at` by a hook that returns the same `strftime` expression, never a JavaScript date. A JavaScript timestamp is taken when the statement is built, before the batch runs, and Workers freeze the clock between I/O, so a row created and updated in one batch, as the pipeline does with a new day album and its first thumbnail, would carry an `updated_at` earlier than its `created_at` and fail the check below. API records keep `updatedOn`, the name the app reads.

The `item` table stays as the prototype shaped it, with three changes: the timestamps above, `thumbnail_id` declared as a foreign key to `item.id` with `ON DELETE SET NULL`, so deleting a photo clears it from the albums it fronts, and two indexes: one on `version_id`, so an object's row is one lookup, and one on `thumbnail_id`, because `ON DELETE SET NULL` has SQLite find every row that points at the deleted one, which without an index is a scan of `item` on every media delete. Both get a rows-read case. The natural key stays `(parent_path, item_name)`, which is the URL scheme; `id` is what other rows reference.

| Column                           | Meaning                                                                                                                                                                                                                                                                                                                                                                                                              |
| -------------------------------- | -------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `id`                             | Integer rowid; the FTS index and `thumbnail_id` key on it                                                                                                                                                                                                                                                                                                                                                            |
| `parent_path`, `item_name`       | `/2001/06-15/` is `06-15` in `/2001/`; `felix.jpg` in `/2001/06-15/`. Unique together. The root is not a row.                                                                                                                                                                                                                                                                                                        |
| `item_type`, `media_type`        | `album` or `media`; `image` or `video` for media and null for an album, by check constraint                                                                                                                                                                                                                                                                                                                          |

Tags are a JSON array typed `string[]`, as the crop is typed a rectangle: no delimiter to collide with a keyword, and FTS5's tokenizer reads the same words out of the JSON text. Nothing shows, edits or filters by tag today; a tag table earns its place, and its join and its own FTS triggers, when something does |

The other tables stay: `user`, `passkey`, `invite`, `spent_challenge` for login; `upload_error` for what the admin UI polls; `probe_result` for the idle-latency probes. One is new:

**`upload`** records every version id the Worker mints, one row per presigned URL: `version_id`, `album_id` of the day album the item goes in, the `item_name` it will have, `target_id` and `target_path` when the upload replaces an existing item, `username` of the admin who asked, and `completed_at` once the pipeline has made it an item. `parent_path` is kept beside `album_id` as the record of what was asked for; the pipeline resolves the album by id, taking its path as it is when the upload lands, so an album renamed while a browser was still uploading into it receives the upload under its new name, and one deleted in the meantime, a row whose `album_id` the database cleared, becomes an upload error. A replacement's target is resolved the same way: `item_name` records the name presign computed, but the pipeline names the row from the target's base name as it is when the upload lands and the extension of `item_name`, so a target renamed in the meantime keeps its new name. AWS keyed uploads by path and recreated a renamed album under its old name. Completed rows stay, as the record of who uploaded what and when; rows that never complete leave with their inbox objects in the purge. It is how the pipeline knows what an object in the inbox is for, since the object's key is only its version id; how the pipeline refuses an object nobody presigned; how a replacement can change an item's type without the pipeline guessing; and how the purge tells an upload that was never finished from one that was.

### What the database enforces

Every rule below is a named `CHECK` in `schema.ts` and so in the baseline migration, beside the `NOT NULL`, `UNIQUE` and foreign-key constraints. SQLite's `CHECK` has `GLOB` with character classes, `length`, `trim`, `lower` and the `json_*` functions, which covers formats and shapes; it has no regular expressions and no subqueries. A rule that is a `CHECK` changes by a table rebuild, which drizzle-kit generates, so they go in complete now, while the tables are empty, and one the real gallery argues with is loosened later.

On `item`:

- **Paths.** `parent_path` is `/`, `/YYYY/` or `/YYYY/MM-DD/`. An album in `/` is named `YYYY`; an album in `/YYYY/` is named `MM-DD`; a media item is in a day album and named `something.ext`, one dot, no slash, nothing blank, and never `.jpeg`: the gallery stores a JPEG as `.jpg`, as AWS did, and the app's sanitizer turns a `.jpeg` file name into one before it asks. This is `isGalleryKey` from `shared/`, as a constraint.
- **Types.** `media_type` is set exactly when `item_type` is `media`. That it is `video` exactly when the name's extension is one `shared/` lists as video is a `gallery/` rule, applied at presign and in the pipeline, not a constraint: a constraint would make supporting a new extension a rebuild of `item`.
- **A media item has a file and a size.** `version_id`, `width` and `height` are set, non-blank and positive for media and null for albums. `version_id` is letters, digits, `.`, `_` and `-`, which admits the ids this Worker mints and the ones AWS assigned. `duration_seconds` is set and positive exactly for a video.
- **Captions belong to one type.** `title` and `tags` are null for albums; `summary` is null for media; `description` is allowed on both. A caption that is present is not blank once trimmed.
- **Tags** are a JSON array. That each element is a non-blank string needs a subquery over `json_each`, which a `CHECK` cannot have, so `gallery/` checks it.
- **Published** is `0` or `1`, and `0` for media, whose visibility is their album's.
- **Thumbnails.** `thumbnail_id` is null for media and references `item.id` with `ON DELETE SET NULL`. `thumbnail_crop` is null for albums and, when set, a JSON object whose `x` and `y` are numbers at or above zero and whose `width` and `height` are positive and fit inside the item's `width` and `height`. That the referenced row is a media item inside the album's subtree looks at another row, so it is a condition of the `UPDATE` that sets it.
- **Timestamps.** `created_at` and `updated_at` are in the format the default writes, `YYYY-MM-DDTHH:MM:SS.sssZ`, and `updated_at` is never earlier than `created_at`. The same two constraints apply to every table.

On the others: a `username` is lowercase letters, digits and underscores, starting with a letter, and every column that names one references `user`; `credential_id` and `public_key` are non-blank and `counter` is at or above zero; an invite's `token_hash` is 64 lowercase hex characters; every `expires_at`, `used_at` and `last_used_at` has the timestamp format; an `upload_error` names a media path and has a non-blank message; an `upload` has a version id of the same shape as `item`'s, a day album path and a media name, an `album_id` that is null or references `item.id` with `ON DELETE SET NULL` and is indexed, since clearing it on an album delete would otherwise scan every upload ever made, a `target_path` that is null exactly when the upload is not a replacement, a `target_id` that is null or references `item.id` with `ON DELETE SET NULL`, so a replacement whose target was deleted before the upload finished is still known to be one, and indexed for the same reason `album_id` is, since every media delete has SQLite look for the uploads that point at the row, a `username` that references `user`, and a `completed_at` that is null or a timestamp; a `probe_result` has a status of null or 100 to 599, timings of null or at or above zero, and `seq` at or above zero.

Rules with a user-facing answer stay in `gallery/`, where a violation becomes a `400` with a message: a day album publishes only if its year is published, a rename keeps its extension, a media name's extension says its type. A constraint failing is a bug, and answers `500`, except through `PUT /api/item`, the import endpoint, which answers `400` with the constraint's name, so a script feeding it learns which rule a row broke.

**The migrations are reset to one baseline.** Both environments hold prototype data, and the seventeen migrations so far rebuild `item` three times. `api/migrations/` starts over with one generated migration for the schema, one raw-SQL migration for the FTS5 table and its triggers, and one for the seed users. The update trigger fires only on `UPDATE OF item_name, title, description, tags, summary`, the columns the index holds, so setting a thumbnail, publishing, pointing a row at a new version or moving an album's children on a rename leaves the index alone; the rows-read test holds each of those writes to the row and its index entries, since the trigger's cost shows in rows written. Each environment's database is emptied by hand, tables and Wrangler's migration record together, before the branch is pushed to staging and again before the merge that releases production, since the release applies whatever migrations the tree holds. Everything in them goes: the passkeys, so every admin registers again through a new invite, and the probe history, whose numbers are already in `docs/Perf.md`. Right before each wipe, `POST /api/backup` writes the rows to `backups/d1/`, and `docs/Perf.md` notes the date the probe table started over. The release's check that the previous version still works on the migrated database will fail on that push, since the previous version's queries meet a schema they were not written for. The script releases anyway but exits non-zero, so that push's Deploy run shows as failed although the new version is serving; and if the new version fails its own check on the same push, the script leaves the broken previous version serving, so that push is watched rather than left to run.

## Storage

Two buckets, as now: the media bucket holds uploads and originals, the derived bucket holds everything made from them.

| Key                                     | Bucket  | Written by                                         |
| --------------------------------------- | ------- | -------------------------------------------------- |
| `inbox/<versionId>`                     | media   | The browser, through a presigned PUT               |
| `originals/<versionId>`                 | media   | The upload pipeline, once                          |
| `derived/<versionId>/<size>[-crop]-fmt` | derived | The image route, on the first request for a size   |
| `derived/<versionId>/video.mp4`         | derived | The transcoder                                     |
| `derived/<versionId>/poster.jpg`        | derived | The transcoder; the source of a video's thumbnails |
| `backups/d1/<timestamp>.json`           | media   | The nightly backup                                 |

**The transcoder writes to the derived bucket**, so `presign` takes the bucket it signs for, each environment gets a `DERIVED_BUCKET` var beside `MEDIA_BUCKET`, with the types regenerated, and `/v/` and the poster read come from the `DERIVED` binding. The MP4 and poster then sit behind the derived bucket's public image host, keyed by version id, exactly as every derived image already is.

**The gallery path is not in the key.** A `versionId` is unique to one upload, so the object needs nothing else, and the row is what says which path a version belongs to. That is what makes a rename, of a photo or of an album with photos in it, a database change alone, where AWS copied every original and every derivative, one object at a time. It also stops forbidding two things AWS never had, moving a photo between albums and renaming a year, which the app does not offer yet. The URL the app uses keeps the path, `/i/2001/06-15/felix.jpg/<versionId>?size=200x200`, though the Worker needs only the version to find the object and reads no row to serve an image. The path is there for whoever reads the URL: in the network tab, the logs, the probe rows and the browser runs, and in the counting of album views by the `/i/<year>/<day>/` prefix that `docs/Perf.md` inherits from the AWS analyses. It also gives `/raw/` the file name for `Content-Disposition` without a lookup. The Worker never checks that the path matches the row, so a URL cached at the edge, in the app's IndexedDB or in an email keeps working after a rename; `/i/anything/<versionId>` serves the image, and the version is the secret. That holds for videos too: on a miss the image route looks for the version's poster before its original, so what the URL's file name ends in decides nothing, at the cost of one extra read each time a derivative is generated, which happens once per size.

What is given up is browsing the bucket by path in the dashboard, and the mitigations are part of the port: `api/scripts/media.ts <gallery path>` prints an item's row and its keys, the `version_id` index answers the reverse question, and each original carries its upload-time path as custom metadata, a label written once and never updated, so a stray object can say where it came from. A listing of `originals/` is in upload order for what this Worker uploaded, since the ids it mints begin with a timestamp; the ids copied from AWS are opaque and sort as they sort.

**The version id is minted when the presigned URL is issued**, a millisecond timestamp followed by 64 random bits, time-sortable and URL-safe, written to the `upload` table with what the upload is for, and made the inbox key, so the app learns it from the presign response and the pipeline reads it from the R2 event and looks the rest up. The URL signs no content type, as AWS's did not, so the browser sends the file's own type and the original keeps it. A redelivered event names the same key, finds the upload already completed, and does nothing.

**Any file may replace any media item.** AWS refused a replacement in another format, a PNG over a JPEG or a JPEG over a HEIC, because an item's identity was its path with the extension in it, and the object's key was that path: the bytes and the name would have disagreed, or the captions would have been lost to a new item. Here the row's identity is `id` and the object's is `versionId`, and albums point at a thumbnail by row id, so a replacement in another format is a replacement and a rename in one batch. The same row gets the new version, size, media type and duration, and its name becomes its own base name with the source's extension as the sanitizer normalizes it, `felix.jpg` to `felix.png`, or to `felix.mov` with the transcoder running as for any video, and unchanged for a `.jpeg` re-export. The `UPDATE` builds that name from the row's name as it is when it runs, which a media name's one dot makes a `substr` and an `instr`, and refuses it as a condition if another row holds it, so a rename of the target while the upload was in flight is kept rather than undone. Captions, tags and every album that shows the item carry over, because none of them named the file. Since the name changes with the type, the rule that the name says the type holds throughout. The one thing that cannot carry over unexamined is the crop, which is pixels of the old image: the batch keeps it only when the new image has exactly the old dimensions, the re-export case, and clears it otherwise, since a rectangle chosen on one photo that happens to fit inside another is a plausible-looking wrong thumbnail, worse than none. The rule applies to every replacement; AWS had none because nothing checked. A new name that another item already holds is refused at presign, and refused again by the pipeline if the collision arrived in between. The media page's URL changes with the name, as it does on any rename; every image URL keeps working, since those are keyed by version.

**Nothing is deleted when an admin deletes or replaces.** The row goes, or points at the new version, and the old objects wait for the nightly purge, which lists both buckets, keeps every version some row references, and deletes the rest once they are 30 days old by R2's own upload time. Restoring a deleted or replaced photo within that month is pointing a row at the old version. The purge is the one destructive job, so it deletes at most 500 objects in a run, a day album's worth of replaced originals with their derivatives, and logs what it left for the next night, which turns a bug that orphaned the gallery into a log line rather than a loss. It keeps nothing between runs: it lists each bucket from the start and deletes as it goes, so a run that dies part way has only done work the next night would do again. The D1 dumps under `backups/d1/` are referenced by no row, so the same rule is their retention: the newest 30 days of nightly dumps are kept. It also sweeps the leftovers of uploads that failed part way. An `upload` row a day old with no `completed_at` is an upload the browser abandoned, after taking its URL or after putting the object, and the URL it took has long expired, so the row is deleted, and its inbox object with it when there is one. An inbox object with no row at all is referenced by nothing and goes by the 30-day rule like anything else.

**Originals are kept as uploaded**, HEIC included. The Images binding decodes HEIC itself, so a HEIC's thumbnail and detail image are cut from it like any other image's, once each and stored, and nothing is converted on the way in. The one place a browser meets the file itself is the app's full-size link, and only Safari can show a HEIC, so for a HEIC original `/raw/` answers with a quality-92 JPEG, made by the Images binding on each request and not stored, since the link is rarely followed and a stored copy would double every HEIC's footprint; `?format=original` gives the file itself. When the binding refuses the file, as it does the 10-bit HEICs in Risks #11, `/raw/` answers with the original bytes instead, so the link still works in Safari and fails nowhere else any worse than it did. AWS converted every HEIC to a JPEG on upload with a hand-built Sharp layer, renamed it and deleted the HEIC, which took HEIC-specific code at every step in the back end and the app; here there are two pieces, that branch in `/raw/` and the thumbnail cut at the end of the upload pipeline that catches a file the binding cannot decode.

## The API

Same origin, JSON, under `/api/`. Every write needs a logged-in admin and answers `401 { "errorMessage": "Unauthorized" }` without one. Reads never refuse: a guest gets the published view and the `x-auth-status` header says which view was served. Every error is `{ "errorMessage": string }` from `shared/`'s error schema, the 404s included, and an unexpected exception is `500 { "errorMessage": "Server Error" }` with the detail in the log, never in the body. The method is dispatched, so a `HEAD`, `PATCH` or `DELETE` reaches its handler.

**Routing is Hono's.** The prototype's chain of `startsWith` checks in `index.ts` dispatched three methods and no path parameters; the table above needs every method, parameters that contain slashes, and one error body from every failure, which is what a router is for. Hono is the one built for Workers: its `fetch` has the Worker's own signature, so it sits in the default export beside the queue and cron handlers and the test helpers call the Worker as they do now; its `onError` and `notFound` hooks are where the error shape lives; and its middleware carries what every response gets, the auth-status and timing headers today and the security and robots headers below, and the admin gate on writes. It stays inside `index.ts` and `routes/`: `gallery/` and the layers under it take plain arguments and return data, never Hono's context, which the import rules hold. Settled when it went in: Hono answers a `HEAD` by dispatching it as a `GET` and dropping the body, before any route is matched, so a `HEAD` route cannot be registered; the raw request keeps its method, so the album and media `GET` handlers read it and answer a `HEAD` with an existence check rather than a full read. Bodies are parsed with `safeParse` at the top of a handler, as before, since every schema is in `shared/` already and the validator would add a second way to say the same thing.

| `POST /api/errors`                      | `{ paths }` → `{ errors: { <path>: message } }` from the last day, as now                                                                                                                                                                                                                                 |
| `PUT /api/item`                         | The whole row of one item, strict. The import endpoint: what `import-album.ts`, the gallery migration and the e2e seed write with, since no other route sets a version id and dimensions                                                                                                                  |
| `GET /api/auth/status`, `/api/auth/*`   | Unchanged                                                                                                                                                                                                                                                                                                 |
| `GET /api/health`, `POST /api/backup`   | Unchanged                                                                                                                                                                                                                                                                                                 |
| `GET /i/<path>/<versionId>?size=&crop=` | Unchanged for readers; the object comes from `derived/<versionId>/`, generated from `originals/<versionId>` or the poster                                                                                                                                                                                 |
| `GET /raw/<path>/<versionId>`           | The original, from `originals/<versionId>`. A HEIC comes back as a full-size JPEG unless `?format=original` asks for the file itself or the binding cannot decode it. The URL loses the `originals` segment it has today; `originalUrl` in `shared/urls.ts` changes and the app, which calls it, does not |
| `GET /v/<path>/<versionId>`             | The MP4 with byte ranges, from `derived/<versionId>/video.mp4`                                                                                                                                                                                                                                            |

The three media routes are not gated on who is asking, as the AWS image CDN was not: the version id is the capability, 64 random bits behind a timestamp for the ids this Worker mints and AWS's opaque 32 characters for the copied ones, and knowing it is knowing the photo. Gating `/raw/` and `/v/` on the item's album being published would add a row read to routes that otherwise read none, and would not protect `/i/` at its largest size, which needs to read none. What the routes can reach is fixed by construction instead: `/raw/` reads only `originals/<versionId>` and `/v/` only the version's MP4, so nothing else in either bucket, the D1 dumps and the inbox included, is reachable through them.

Kept for measurement, since `docs/Perf.md` and `docs/Risks.md` still use them: `/i2/*` for the second-bucket experiment, the idle probes and browser runs and their crons, `/api/seed` and `/debug/image/*` behind admin login. Removed: `GET /api/ryw`, an unauthenticated write built for a risk since closed; `PUT /upload/*`, a stand-in for the presigned PUT that tests no longer need since they can put an object and drive the queue themselves; and `POST /api/upload-url`, the prototype's presign, which `POST /api/presigned` replaces.

Uploads are validated at presign: the album exists and is a day album, each path is a strict media name in that album, lowercase with underscores, an extension on the lists in `shared/paths.ts` and `.jpg` never `.jpeg`, which is what the app's sanitizer produces, a path with no `replaces` names no existing item, and a `replaces` names an item in the album whose base name the path keeps and the path names no item other than that one, so the admin who drops a PNG on `felix.jpg` beside an existing `felix.png` hears so before the upload, not after. The pipeline trusts nothing else: an inbox object with no `upload` row is left for the purge, and one whose row is complete is a redelivery, which deletes the object and does nothing else.

The extension lists are AWS's, from `galleryPathUtils.ts` in `tacocat-gallery-sam`: jpg, jpeg, png, gif, heic and heif for images, and mp4, mov, avi, m4v, mkv, webm, 3gp, mpg and mpeg for video. They move into `shared/paths.ts`, and the app's `galleryPathUtils.ts` imports them rather than keeping its own copy. So does the sanitizer that makes a file name a strict media name, lowercase, underscores, `jpeg` to `jpg`, which today lives only in the app, so that the app normalizes with the same function the Worker refuses by, and `PUT /api/item` refuses a `.jpeg` name while taking the older, unsanitized names the AWS gallery holds. What a name may be is then one module, read by both sides and copied once into the `CHECK` on `item`. The four-extension video list the prototype wrote from what the gallery holds goes: with it, a `.webm` the app accepts is treated as an image by the Worker and fails in the EXIF reader.

### Search

FTS5 over `item_name`, `title`, `description`, `tags` and `summary`, as now. The caller's terms become an FTS query by quoting each word, so no input is a syntax error. Results are sorted by gallery path, newest first unless `oldestFirst`, filtered to the years asked for, paged with `pageSize` and `startAt`, and `total` counts every match. Guests see published albums and the media in them, which AWS did not filter.

### The upload pipeline

The R2 event for `inbox/<versionId>` reaches the queue consumer, which starts a Workflow instance for it, named by the version id so that a redelivery starts nothing, and the instance, in steps each retried on its own and none of which hands the file to the next: finds the `upload` row for that version, and stops if there is none, or deletes the object and stops if the row is complete; reads the file; for an image, reads its size, caption and keywords with ExifReader (`api/src/media/exif.ts`, which reads the IPTC fields a JPEG carries and the XMP ones a HEIC or PNG has), and for a video, has the container transcode it to `derived/<versionId>/video.mp4` and `poster.jpg` and report its size and duration; writes the original to `originals/<versionId>` with the path in its metadata; then in one batch inserts the item under the album's current path, read from the `album_id` row inside the insert, or for a replacement updates the target row, named from its own current base name and the upload's extension, makes the first upload into a day its thumbnail, clears any upload error for the path, and marks the upload complete; the pipeline creates no album, since presign refused any upload into one that was not there; then generates the thumbnail and the detail image, the two sizes the album page and the media page are about to ask for, so the first reader never waits for a transformation, as AWS's upload Lambda did for the detail image, and a stored derivative is found only by the exact key the app asks for, so the detail size rule, 1024 on the long side and never enlarged, moves from the app's `MediaBaseImpl` into `shared/urls.ts` and both call it; and last deletes the inbox object. That is two transformations per upload, a small fraction of the 5,000 a month the Images allowance includes. A replacement is not destructive: it sets the name, version, media type, size and duration, keeps the crop only if the dimensions are unchanged, and leaves an existing title, description and tags alone, taking the file's caption only where the row has none, `title = coalesce(item.title, ?)` in the `UPDATE`, where the prototype's upsert overwrote every column. A replacement whose target was deleted while the upload was in flight, an `upload` row with a `target_path` and no `target_id`, becomes an `upload_error` saying so, and the object is left for the purge; an upload whose album was deleted, a row with no `album_id`, and a name the pipeline finds taken by another item are the same kind of error. A file that is not what its name says becomes an `upload_error` row and is dropped, not retried. So does a HEIC the Images binding cannot decode: the thumbnail cut at the end is where that surfaces, so the admin sees the file named in the upload status rather than a broken image in the album.

## Headers and robots.txt

The site has no public presence: every page is `noindex`, AI training is refused, hotlinking is refused. On AWS that is CloudFront's work, in `tacocat-gallery-hosting-aws`'s `template.yaml`: a function that serves `robots.txt`, and two response-header policies. Here only one of those rules exists, the immutable `Cache-Control` on `/_app/immutable/*` in `web/static/_headers` and on derived images, and `docs/plans/Release.md` lists the rest as owed. The port carries them over:

- **`robots.txt`**: `User-agent: *` with `Allow: /`, so ordinary crawlers fetch pages and see the `noindex`, where a `Disallow` would hide it and leave bare URLs listed. The `Disallow: /` block for the AI training bots is Cloudflare's: the zone's managed robots.txt setting prepends its block, with a list longer than the CloudFront function's and kept current by Cloudflare, to whatever the origin serves at `/robots.txt` with a 200. The origin has to serve a real text file there, since the app's fallback would otherwise answer with `index.html` and Cloudflare would prepend to that. A static file in `web/static/`.
- **`X-Robots-Tag: noindex, noimageindex, nosnippet, max-image-preview:none, notranslate, noarchive, noai, noimageai`** on every response, which is how `noindex` reaches images and anything already indexed, since the app's meta tag covers only its own markup. And `tdm-reservation: 1`.
- **Security headers** on every response, with the template's values: `Strict-Transport-Security`, `X-Content-Type-Options: nosniff`, `Referrer-Policy: strict-origin-when-cross-origin`, `X-Frame-Options: DENY`, and its `Permissions-Policy` with camera, geolocation, microphone and the rest turned off.
- **`Cross-Origin-Resource-Policy: same-site`** on `/i/*`, `/v/*` and `/raw/*`, so another site cannot embed the photos. AWS sends it in production only, because its local dev server loaded images from the staging image host and `localhost` is same-site with nothing; here the media routes are on the site's own origin in every environment, `wrangler dev` included, so the header is unconditional and staging's tests assert the real value.
- **Not carried over**: the image CDN's `Timing-Allow-Origin`, which let the app read full Resource Timing entries for thumbnails across origins. Same-origin timings are never withheld, so it has no job here.

The app shell needs nothing beyond the immutable rule already in `_headers`. AWS cached `index.html` under CloudFront's CachingOptimized policy, so a deploy had to invalidate it, and mapped 403 and 404 to `index.html` as custom error responses; Workers serves assets with `Cache-Control: public, max-age=0, must-revalidate` and an ETag, and `not_found_handling: single-page-application` is the error mapping.

`robots.txt` asks; the zone enforces. `infra/main.tf` already sets the zone's `ai_bots_protection` to block, which turns known AI crawlers away before they reach the Worker. The file is for crawlers that honour it, for whatever the zone's list misses, and for the record.

Two places serve responses, so the headers live in two places. The app's pages and files, the not-found fallback to `index.html` included, never reach the Worker, so theirs go in `web/static/_headers` as a `/*` block beside the immutable rule. Everything the Worker answers itself goes through the wrapper in `index.ts` that already adds `x-auth-status`, `x-worker-colo` and `server-timing` to every response, so it is one block there. Tests: an integration case asserting the set on an API response and an image response, a stack test asserting it on the app shell and on an app route's fallback, since the asset router serves those and that is the thing to confirm rather than assume, and one for `robots.txt`'s body.

## Layers

```text
api/src/index.ts   the composition root: fetch, queue and scheduled handlers, wired to the layers below
api/src/routes/    HTTP, on Hono: parse the request, gate on the admin, call gallery/, shape the response

api/src/util/      helpers with no layer, such as running work in sequence
```

The rules, each an ESLint `no-restricted-imports` block as the web app's layers are, plus `import-x/no-cycle` over the Worker and `shared/`. The web app is left out of the cycle check: its album models cycle, as they did in the AWS app, and untangling that is a change to the app.

- `routes/` imports anything below it; nothing imports `routes/`.
- `gallery/` imports `db/`, `storage/`, `media/` and `shared/`, never `auth/`, `ops/` or `http/`. Who is asking arrives as a boolean; the transcoder is handed presigned URLs, since `media/` cannot make them.
- `auth/` imports `db/`, `http/` and `shared/`.
- `ops/` imports `gallery/`, `db/`, `storage/`, `http/` and `shared/`.
- `http/`, `db/`, `storage/`, `media/` and `util/` import `shared/` and not each other; every layer may import `util/`.
- Modules within a layer may import each other. Tests are exempt.

## The web app

Two changes, both because the platform differs, and the layering rules of the app hold. All of it is admin-only code, so the reader's path, which the performance comparison measures, is untouched.

1. **The presign request says what each upload is, and the response carries the version id.** `s3Upload.ts` sends `[{ path, replaces? }]` and reads `{ url, versionId }` per path instead of the `x-amz-version-id` response header, which R2 does not send. The app computes `path` for a replacement, the target's base name with the new file's extension as the shared sanitizer normalizes it, which is what `getUploadPathForReplacement` becomes and what the Worker checks; the jpg/jpeg case is the sanitizer's rule, not a branch of its own. The album drop zone sends `replaces` for every colliding name, same extension included, since a path without it may name no existing item; `enrichWithPreviousVersionIds` already finds those names. This change lands with 8b, since the browser upload that ends that commit is made through the app; the rest of the app's changes wait for step 10.
2. **Any file replaces any item, and completion is by version id.** `getReplacementExtensionError` goes. Completion becomes one rule for every case: after the refetch, the album holds a media item whose `versionId` is the one presign returned, found by scanning the album rather than by path, so the rule does not care whether the replacement renamed. A replacement that changes the extension changes the media page's URL, so the replace button and the drop zone go to the album as soon as the upload is asked for, as the rename button does, and the album page shows the upload status; the machines navigate nowhere, as none does today. A replacement in the same format stays on the page, which refreshes in place.

With no rename on the server, the "renamed on server" concept that HEIC needed is dead code end to end, and step 10 removes it rather than leaving a branch that can never run:

- `fileFormats.ts`: `getMediaPath` and `isRenamedOnServer` go. What remains per format is two browser facts, `browserCanDisplay` and `getProcessingTimeout`, which is a small table, not a handler registry.
- `models/album.ts`: `UploadEntry` and `MediaItemToUpload` carry an `uploadPath` and a `mediaPath` that are now always the same, and every comment on them explains HEIC; they become one path. `previousVersionId` existed only because a converted HEIC's upload id said nothing about completion; it goes.
- `uploadUtils.ts`: `isUploadComplete` is one comparison, `findProcessedUploads` asks whether the album holds a version rather than what version is at a path, and `enrichWithPreviousVersionIds` shrinks to returning the colliding names and setting `replaces`, under a name that says so, or inline in its callers if that is three lines.
- `UploadMachine.svelte.ts` stops calling `getMediaPath` when it builds entries.
- What stays: the HEIC mentions in `mediaValidation.ts` and `UploadThumbnail.svelte`, which are about whether the browser can preview a HEIC, true on any platform; and both rename machines, which post, refetch the parent and drop the old path, since AWS's copies and its size cap never reached the app.
- A rename no longer leaves the page. The buttons sent the admin to the parent because a rename on AWS copied objects and took seconds; here it is one statement, so the page stays, shows its rename-in-progress page, and once the machine records that the server has renamed the item, the routing component moves to the new path in place of the old one in history. A refused rename leaves the admin where they were, with the toast.
- The app's `galleryPathUtils.ts` already imports the extension lists from `shared/paths.ts`; the sanitizer follows them there, and what stays in the app is display helpers.
- Also, in the same commit: the `?fresh` flag and the per-album `albumChangedAt` bookkeeping in `AlbumState.svelte.ts` and `AlbumLoadMachine.svelte.ts` exist to get past CloudFront after a save. The Worker ignores `?fresh` already, the bookmark cookie makes an admin's read after their own write consistent, and the upload poll, whose write is the queue consumer's, retries until the item appears, so `reloadAfterChange` can be a plain fetch and the bookkeeping can go. And `s3Upload.ts`, `uploadToS3` and the S3 comments in the models are misnamed now; the commit touches those files, so it renames them.

Everything else the Worker conforms to: the paths and bodies above are the app's, `errorMessage` is what it already reads, and its `?fresh` re-read after a save is answered by the bookmark cookie the write set.

What the upload found. Every file became an item with its thumbnail, HEIC and orientation included, so the pieces work together; the speed did not: 52 files took 97 s, one every 1.6 s, where AWS's Lambdas did fifty as fast as one, and the app stops waiting after 15 s. The cause is Queues, not the Worker. It adds consumers only between batches and only as a backlog grows, and Cloudflare's own metric showed 1 to 2.6 consumers on that drop, 1.6 on a second, and 4.6 once the batch size was one, which got 21 PNGs done in 27 s. R2 can raise its event into nothing but a queue, so the queue stays as the event's record, and the consumer now starts one Workflow instance per event, named by the version id, which is where the fan-out AWS had from S3 events comes from on this platform: each upload gets a Worker's memory to itself and each step its own retries, and a failed instance keeps its state for 30 days. Two smaller things it taught: `scripts/release.sh` releases versions with `wrangler versions upload`, which leaves a queue consumer's settings as they were, so a consumer change ships with `npm run deploy --workspace api`, like a transcoder change; and the batch size stayed at one, since the consumer does nothing but start an instance and waiting to fill a batch would add the batch timeout to every upload.

### What the first steps taught

For the sessions doing the rest, things a fresh session would otherwise find out the hard way:

- Branch from `main` after the previous step merges, and never `git stash` mid-step: a step's new files are untracked until staged, and a stash drops them from the tree.
- A step is one commit, and the pre-commit hook runs every suite the staged files touch, so a commit takes about 40 seconds. Commit once, when the step is green, rather than in pieces.
- The test helpers to reach for are `call`, `callAsAdmin` and `parseExactly` in `api/test/helpers.ts`. A stack test can import a constant from `api/src` to hold two copies of something together, as the headers test holds `web/static/_headers` to the Worker's values.
- What Hono does with `HEAD`, a mid-path `*` and a guest's write is under The API above; read it before adding a route.
- `import-x/no-cycle` sees `.ts` files only because the config names the extension; the comment there says so, so it is not a setting to tidy away.
- Wrangler's local Durable Object reset prints `Application called deleteAllDurableObjects()` as an uncaught exception during the tests. It is the Vitest Workers plugin's storage isolation, not a failing test.
- The stack tests start their Worker with no persisted storage, so D1 there has no tables at all; a route that reads D1 answers 500 there, which the routing test never looks at. List only paths that need no database in that test.
- **The write pattern is built; reuse it.** A gallery write is one statement whose cross-row rules are `EXISTS` subqueries in its `WHERE`, returning `Written`, the changes and D1's meta, from `api/src/gallery/writes.ts`. When it changed nothing, one read of subselects, `describeAlbum` or `describeMedia`, says why, and the route turns that into the 400 or 404 with the message the AWS lambda used. Routes read bodies with `parsedBody` and answer with `wrote` from `api/src/routes/requests.ts`, 204 with the bookmark cookie, which is all the app checks. The rows-read test has a case per write; add one for each new subquery.
- A Drizzle query builder is changed by what is called on it, so a builder reused for several subqueries silently gives them all the last `where`. Start each from `database.select()`.
- Drizzle's `run()` returns rows under their SQL column names, not the builder's aliases, so name a computed column in SQL with `.as()`; its `batch()` returns rows without D1's meta, so a write whose cost is watched runs its statements one at a time.
- D1's `meta.changes` counts what the FTS triggers wrote too, so a write tests for more than zero changes, never exactly one.
- A `CHECK` whose expression comes out `NULL` passes, so every constraint says what must be non-null, and D1 refuses a GLOB pattern over 50 characters, so a long format is checked in pieces or by a `strftime` round trip. `api/test/db/constraints.test.ts` tries every rule by name; add a row there for a new one.
- A statement in a `batch()` has to come from a query builder: Drizzle's D1 driver cannot batch a raw `sql` statement, and its insert from a select takes every column of the table, in the table's order, each aliased to its column name. `insertItem` in `api/src/gallery/upload.ts` is the example.
- The test admin is `moses`, a seeded user, because a presign records who asked and `upload.username` references `user`; a cookie for a made-up name gets a foreign key error on the first write that records it.
- `eslint --fix` turns `expect(a > b).toBe(true)` into `toBeGreaterThan`, which throws on strings. Compare timestamps with `Date.parse`.
- Presign takes only strict media names, what the app's sanitizer makes, so a test stages an upload under a lowercase name with underscores, not a fixture file's own.
- D1 binds at most 100 parameters to one statement, so rows go in as a batch of single-row inserts, never one multi-row insert; a drop of 52 photos found the presign insert doing the latter. Local D1 enforces the limit, so a test with a day's worth of rows catches it.
- A local Worker can consume no real queue, Wrangler's remote bindings leave Queues out, so under `wrangler dev` an upload could never complete: the browser's PUT went to the account's bucket and its event to the deployed Worker. Step 5 removed the prototype's stand-in on the grounds that the tests drive the queue themselves, which a person cannot. `UPLOADS=local` in `.dev.vars` brings the stand-in back as Cloudflare's local-first workflow wants it: presign answers with the Worker's own URL, `PUT /upload/<versionId>` puts the file in the local inbox and sends the local queue the message R2 would, and the pipeline runs unchanged. The e2e stack runs the same way, so its upload journey ends with the item in the album.

## Afterwards: copying the gallery

A later plan, but the design above is shaped for it, and its first part exists: **`check-gallery.ts` runs the constraints over the production gallery's data and reports every row they refuse.** There are reasons to expect some: AWS's image type had `dimensions` optional and its repo carries a dimensions-repair migration with an "unfixable" count, so some rows may lack a size; blank captions, an unlisted video extension, or a name outside AWS's own rule of letters, digits, underscore, hyphen and one extension, which came long after most of the uploads, are all possible in 25 years of them. A scan of the production table is under a penny by the AWS repo's `docs/Migrations.md`, or failing AWS access, every published album through the public API, which is most of the gallery but not the drafts. The copy then repairs rows, reading a missing size from the original, or a rule the gallery argues with is loosened by a table rebuild.

Each current original in the AWS bucket is copied to `originals/<its S3 versionId>` with its path in the metadata. S3 documents its version ids as opaque, and its own example contains `/` and `+`, which the URL parser and the `version_id` constraint would both refuse; a sample of 76 ids from three production albums on 2026-09-24 were all 32 characters of letters, digits, `.` and `_`, so the copy checks every id against both and mints a new one for any that fails. Copied ids carry no timestamp, which is why the purge judges age by R2's upload time rather than by the id. The rows come from a DynamoDB export written through `PUT /api/item`, with `itemType` and `mediaType` finished on the way; media rows go in before any album's thumbnail is set through `PATCH /api/album-thumb`, since the foreign key needs the media row to exist. The derived bucket is not copied: derivatives regenerate on request. The observed rate, about 7,700 distinct variants a month and 7,100 without bots, is above the 5,000 the Images allowance includes, so expect about $1 to $1.35 a month at $0.50 per 1,000 after the copy, which the Spending rules want said out loud; a backfill of the newest albums, if the first readers should not wait, is more of the same. `docs/Migrations.md` in the AWS repo has the lessons that apply: idempotent, resumable, newest albums first, diagnose before fix.
